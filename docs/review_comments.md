# RAG大模型API超时兜底：问题分析+业界标准做法+结合你项目现状落地
> 背景：项目 `zz‑demand-system/app/rag/chain.py` 是RAG主链路，分为：查询改写 → Hybrid检索 → LLM生成回答，**LLM调用超时属于外部依赖故障**，会直接打断整条对话链路；当前代码里只做了基础异常捕获，缺少分层兜底策略。

## 一、先区分2类超时
1. **连接超时connect_timeout**：网络不通、DNS错误、代理失败，连不上大模型网关
2. **读取超时read_timeout/generate超时**：大模型服务负载高、长上下文、限流，请求发出去了，但是返回响应慢/中断（流式SSE场景最容易遇到，你的接口是SSE流式输出）

> 你的项目是SSE流式输出 `api/conversations.py::query_conversation_stream`，一旦LLM流式请求超时，会直接抛出异常，**BackgroundTasks会丢失assistant消息，对话状态损坏**（就是评审里的问题6）。

## 二、业界标准完整兜底方案（生产级RAG通用）
分为五层：**超时参数配置 → 重试策略 → 降级兜底策略 → 会话状态保护 → 可观测告警**

### 1）第一层：合理设置超时时间（基础，必须配置）
不能统一设置一个超大超时，要区分链路不同环节
- 查询改写（短prompt）：read_timeout=15‑20s
- RAG主生成（长上下文+检索上下文）：read_timeout=45‑60s
> 不要设置 >90s，HTTP网关、Nginx、FastAPI、浏览器SSE大多有60s左右默认超时，就算大模型还在跑，网关直接切断连接。

> 你的现状：langchain OpenAI客户端没有精细化区分每个环节的超时，全部共用同一个超时，改写环节浪费等待时间。

### 2）第二层：指数退避重试（只对可重试错误）
> ⚠️ **不是所有异常都可以重试！**
✅ 可以重试：连接超时、5xx服务端错误、限流429
❌ **禁止重试**：400参数错误、401鉴权失败、上下文超长、内容审核拒绝；**用户问题已经发给LLM，部分流式返回后发生超时，绝对不能重试**，会造成重复回答、重复计费。

业界标准：
- 指数退避：`backoff = min(base * 2^retry_count, max_backoff)`，例如初始1s，2s，4s，最大8s
- 最大重试次数：**2次**，不要无限重试；RAG场景检索已经执行完，反复重试会拉长用户等待。
- 区分：**查询改写环节可以重试；主回答生成流式环节谨慎重试**，流式跑一半超时，重试会重新生成一遍，浪费token。

LangChain自带 `RunnableRetry`，可以对不同runnable单独配置重试，改写链单独配置重试，生成链少重试。

### 3）第三层：多级降级兜底（核心业务逻辑，RAG生产最关键）
> 当重试耗尽依然超时，不能直接抛500给用户，分3级降级：

#### 降级A：仅查询改写超时
> 查询改写失败，不阻塞业务，**直接使用原始用户query做检索**，返回给用户提示：`「系统处理查询时短暂异常，将按原始问题检索」`
> 这是绝大多数企业RAG的做法，改写是优化项，不是强依赖。

#### 降级B：主LLM生成回答超时（最常见）
分两种模式：
1. **模式1：保留检索上下文，返回片段+提示（推荐中小型企业）**
> 已经拿到检索出来的文档片段，直接把检索到的参考片段返回前端，告诉用户：
> `大模型服务响应超时，为您直接返回检索到的参考资料，请查阅参考片段；您可以重新提问。`
> ✅ 优点：已经消耗的检索成本不浪费，用户至少拿到材料，不是空白报错；
> 你的系统已经拿到sources，完全可以实现这个降级。

2. **模式2：多模型熔断切换（中大型企业）**
> 维护多套LLM后端，主模型超时，自动切备用模型（例如GPT‑4o超时切qwen‑plus），前提：prompt、输出格式兼容。
> 中小型企业成本高，一般不优先搞。

❌ 反模式：超时直接返回“系统繁忙，请稍后重试”，用户完全拿不到已经检索好的资料，检索算力白白浪费。

#### 降级C：检索环节本身超时（PG/向量库慢）
跳过向量增强，切free‑chat模式，告知用户：知识库检索暂时不可用，将直接大模型对话。

### 4）第四层：会话状态保护（针对你的SSE流式架构重点）
> 你的痛点：SSE流式中途超时抛出异常，BackgroundTasks不执行，assistant消息没有落库，对话上下文损坏。
**业界标准：**
1. 流式链路禁止把assistant消息落库交给BackgroundTasks；
2. 发生超时/异常时，必须把**部分生成内容/降级兜底内容，强制写入会话DB**；
3. 在DB标记消息状态：`status: ["partial","complete","error"]`
    - `partial`：大模型中途断连，有部分返回内容
    - `error`：完全失败，填入兜底提示文本
前端读取消息状态，展示对应的提示，**不会出现只有用户问题，没有回答的残缺对话**。

> 很多开源RAG系统都踩过这个坑：流式异常会话残缺。

### 5）第五层：埋点、告警、熔断
1. 埋点：统计超时类型，区分：改写超时、生成超时、检索超时；记录错误标签；
2. 熔断：滑动窗口，短时间内大量LLM超时，触发熔断，直接走降级，不再调用LLM，避免压垮上游大模型API；
3. 告警：超时率超过阈值（比如>5%）推送告警。

## 三、结合你现有项目 `zz‑demand‑system` 的可落地改造建议
文件位置：`app/rag/chain.py`、`app/api/conversations.py`

1. **拆分Runnable，给不同环节设置独立超时、独立重试**
```python
# 查询改写runnable：短超时，允许2次重试
rewrite_chain = _rewrite_query.with_retry(max_attempts=2)
# 主生成链：长超时，禁止重试，流式一旦开始重试会重复输出
generate_chain = rag_generate_chain
```

2. 查询改写捕获超时异常：捕获 `TimeoutError`、`APIError`，降级使用原始query。

3. SSE流式生成外层捕获LLM超时异常：
- 捕获超时后，**不要直接抛出异常终止流**；
- SSE输出兜底事件，把检索到的sources带上；
- **同步写入DB一条assistant消息，status=error，内容为兜底文案**；
> 绝对不能依赖BackgroundTasks保存消息。

示例SSE伪代码：
```python
try:
    for chunk in stream:
        yield build_sse_event(chunk)
except TimeoutError:
    # 超时兜底：返回检索片段，同时落库，修复会话残缺问题
    fallback_content = "⚠️大模型服务响应超时，为您返回检索参考资料：\n" + format_sources(sources)
    yield build_sse_event(fallback_content)
    # 同步落库，不是BackgroundTasks！
    save_assistant_msg_sync(conversation_id, fallback_content, sources, status="error")
```

4. DB消息模型增加status字段，前端识别error/partial状态渲染提示。

## 四、业界常见误区（避坑）
1. ❌ 一超时就无脑重试：流式生成已经吐出一部分token，重试会造成重复回答，消耗双倍token；
2. ❌ 设置超大超时时间，掩盖上游大模型服务不稳定：网关、浏览器SSE有硬性上限，再大超时也会被切断；
3. ❌ 超时直接返回500错误，丢弃已经检索完成的文档片段；
4. ❌ 异常场景消息不落库，造成对话上下文损坏，后续多轮问答全部错乱（你当前代码存在这个风险）。

## 五、中小型企业RAG落地取舍建议
> 你的场景：中小企业内部知识库，不需要复杂多模型熔断。
**优先落地顺序：**
1. 精细化超时配置 + 查询改写环节有限重试；
2. LLM生成超时降级：返回已检索的参考片段，给到用户；
3. 修复SSE异常消息落库，增加消息status状态，解决会话损坏；
4. 埋点监控超时指标；
5. （可选）后期再做多模型降级熔断。

> 补充：合规审查模块（compliance）同样会遇到LLM超时，合规业务要求更高，**合规场景不建议返回半生成结果**；合规链路超时，直接标记审查任务状态失败，记录错误日志，支持任务重新发起，不能把不完整的风险报告返回给业务。
